# Кейс: от сообщения клиента до контролируемого результата

Учебная торговая компания получает обращения и счета из разных каналов. Проект показывает, как сохранить контекст обработки, назначить ответственность и сделать исключения видимыми. Это проектная модель, не обследование реального заказчика.

## Основной сценарий: обращение о двойном списании

1. Сообщение принимается из UI или через интеграцию; повторная доставка возвращает исходный ID.
2. FastAPI классифицирует обращение и готовит черновик. LOCAL — правила, LIVE — внешний LLM.
3. Независимая политика проверяет признаки финансового риска и неоднозначности.
4. Создаётся задача, а при необходимости — согласование с исходным текстом и рекомендацией.
5. Manager/admin принимает решение. Operator не может обойти запрет прямым API-запросом.
6. Решение меняет внутренний статус и сохраняет аудит. Платёж и отправка ответа клиенту не выполняются.
7. Явная передача в CRM создаёт лид с внешним ID. Повтор возвращает прежний результат; неопределённый исход требует сверки.

Приёмка: задача и согласование существуют; две конкурентные попытки решения не дают два итога; повтор обработки не создаёт лишнюю задачу; запись CRM с потерянным ответом не создаётся слепо повторно.

## Второй сценарий: счёт с расхождением

Система извлекает поля из поддерживаемого файла, проверяет структуру и сравнивает с заявкой. Сотрудник видит ожидаемые и фактические суммы и позиции. При расхождении поля, сравнение, связь с заявкой и согласование сохраняются до возврата успешного результата.

Приёмка: документ находится на согласовании, а не зависает в `processing`; повтор защищён; решение согласовано с состоянием документа и аудитом.

## Что обнаружили проверки

- Ранний выход из обработки счёта оставлял несохранённый документ — перенесено сохранение до возврата результата.
- Два обработчика обращений давали разные эффекты — обработка UI/n8n сведена к FastAPI.
- UI ожидал другой формат полей — исправлены контракты списков.
- Ошибочные пакеты могли получать `success` — ошибки фиксируются, retry использует список неудачных записей.
- Оценка правил выявила пропуск обмена — добавлен независимый контроль; исходный отчёт сохранён.
- Браузерный показ обнаружил отсутствие номера заявки в образце — образец исправлен.
