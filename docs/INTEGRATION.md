# Интеграция с Битрикс24: учебный контракт

Выбран Битрикс24 как один конкретный пример внешней CRM. Опыт эксплуатации реального портала не заявляется.

Маршрут: вход → n8n → каноническая обработка FastAPI → проверка необходимости согласования → CRM-адаптер → журнал результата. Ожидающее согласования обращение не передаётся; после решения экспорт вызывается явно.

Используются универсальные [crm.item.list](https://apidocs.bitrix24.com/api-reference/crm/universal/crm-item-list.html) и [crm.item.add](https://apidocs.bitrix24.com/api-reference/crm/universal/crm-item-add.html), `entityTypeId=1`. Схема сверена с официальной документацией 3 ноября 2026 года. На реальном портале надо отдельно проверить доступность REST, режим с лидами, права и обязательные поля.

| Внутреннее поле | CRM |
| --- | --- |
| Краткое резюме | `title` |
| UUID обращения | `originId` |
| Фиксированный источник | `originatorId=opspilot` |
| Категория и внутренний ID | `comments` |

Контакты клиента и полный исходный текст не экспортируются. Лид используется как учебный контейнер; тип сущности реального внедрения выбирают после обследования процесса.

Перед созданием выполняется поиск по внешнему ID. При потере ответа после write доставка получает `uncertain`; повтор сначала ищет запись. Если её нет, остаётся необходимость ручной сверки. Уникальность этих полей на стороне CRM не предполагается.

Проверено: локальный HTTP-контракт, обработка ошибок, потеря ответа после создания, повтор, запрет operator, запрет до согласования. Workflow исполнялся настоящим одноразовым n8n с Manual Trigger и синтетическими credentials. Это подтверждает работу нод, но не проверяет вход production-webhook или конкретный CRM-портал.

Секреты, инфраструктура приложения и полные workflows остаются в приватной реализации. [Видео](DEMO.md) показывает локальный контрактный сервер, что явно указано в титрах.
